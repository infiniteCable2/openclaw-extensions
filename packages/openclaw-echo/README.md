# Echo devices

This plugin exposes assigned Techo5 devices through OpenClaw's native paired-node transport. It uses the existing device inventory for device identity and agent grants. The current OpenClaw fork supplies the private requester and capture storage APIs used here.

## Configuration

Load the device-management and Echo plugins. Register the Echo package directory as the `echo` provider in `plugins.entries.device-management.config.providers`. Add a device to the inventory with `kind: "speaker"`, `provider: "echo"`, and the appropriate agent grants. Its inventory ID goes into `plugins.entries.echo.config.devices[].id`.

Each Echo binding includes its exact paired `nodeId`, the private requester `profileId`, and the allowed native `commands`. An optional `channels` list narrows the message channels. An optional `sessionKey` limits use to the exact host-resolved conversation, including when several devices share the same channel type. Use the canonical key of an existing conversation. The profile must be verified by the current turn. The native node advertises its available commands at connect time. Approve any change to the device's command set through the normal `nodes pending` and `nodes approve` flow. The global native deny list still applies. The plugin supplies the default native command policy for Linux Echo nodes.

`device_inventory` shows the managed device ID. `echo_status` uses the inventory's `read` grant, `echo_control` uses `control`, and `echo_capture` uses `observe`. Each tool uses a `device` and `action` plus the action-specific fields below. Each action also needs the exact corresponding native command in the per-device configuration. Incoming raw `node.invoke` calls cannot substitute for a private agent invocation through these tools. Native command declarations are sufficient for this integration. The device does not need to publish a second dynamic tool catalog.

## Command contract

The Gateway dispatches a regular `node.invoke.request`. Echo replies with the matching invocation ID and `nodeId` through `node.invoke.result`. Successful commands return their values in `payload`. The control tool removes the inventory ID and action before dispatching arguments. It sends an idempotency key tied to the run, call, node and command. The client can return an existing receipt where its corresponding local operation supports replay protection.

## Capture and future playback

The device owns capture admission. It checks the local camera or microphone setting and physical privacy state. Each capture command also requires an explicit native `gateway.nodes.commands.allow` entry. The Gateway bounds and validates the JPEG or PCM WAV bytes, rechecks authorization at the media-store write, and returns a private `FILE:` reference. The capture tool does not automatically attach or publish that file. This integration uses the regular channel media flow for separately authorized sharing.

The native HTTP byte-download path is `/api/artifacts/download/<connection>/<ticket>` on the paired Gateway HTTPS origin, with the configured Gateway base path when applicable. Native byte responses support GET, HEAD and byte ranges. Echo playback still needs a grant that is bound to the target node and the source artifact for its lifetime. Clients must reject redirects and accept only the exact paired origin and allowed path. File-backed playback, video capture and live media are pending their own transport and device checks.
