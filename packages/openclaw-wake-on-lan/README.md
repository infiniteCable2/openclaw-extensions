# Wake on LAN

Native optional tool plugin for one explicitly configured magic packet per
request. It uses Node's UDP support, with no shell, Python service, additional
network dependency, discovery, retries, power toggles or shutdown support.

- `wake_on_lan({ device })`: requires the current agent's `control` grant.
- `wake_on_lan_status({ device? })`: requires `read`; reports configuration
  readiness **without network traffic**. It does not detect whether a PC is on.

`device_inventory` advertises the `wake_on_lan` capability and appropriate
tools. Device management owns names, kind, site, room and grants. This provider
owns only the target MAC, explicit IPv4 destination, UDP port and send timeout.
There is no second inventory or agent ACL: the provider's target entries are
referenced by the central inventory's device IDs.

Only device IDs are model-facing inputs. Unknown arguments, including raw
MAC/IP/port overrides, are rejected. Both the endpoint and grants are read from
the current canonical OpenClaw config immediately before sending, including
after the asynchronous socket bind. Disabling the provider or revoking a grant
prevents a pending send. Already submitted datagrams cannot be recalled.

## Configuration and installation

The accompanying [Example computer template](examples/computer.example.json)
is **not a deployable configuration**: replace the MAC, IPv4 and room
placeholders. It assigns `computer_owner`, named **Example computer**, kind
`computer`, to **example_owner only** at the fictional site `home_site`.
Agent IDs, device IDs, display names and site labels in this example are
illustrative, not production identities. Keep any personal mapping outside
the repository. Confirm the actual identities, site and room before activation.
Merge the example into the
existing registry/profile; do not replace existing providers, devices, grants
or tool allowlists. Add WoL tools to the existing per-agent optional-tool
allowlist using its native configuration mechanism.

Requirements:

1. Verify the target NIC's actual MAC and local subnet broadcast address.
   Do not derive a broadcast address from the last IP octet or assume `/24`.
2. Enable Wake-on-LAN in the target's firmware/NIC/OS as required. Support in
   shutdown versus sleep varies; Wi-Fi wake requires explicit hardware support.
3. The sending Gateway must reach that LAN. Configure a private IPv4 destination
   or the limited broadcast `255.255.255.255`, normally UDP port 9. The packet
   has IP TTL 1. No public endpoint, router port forwarding or remote-site
   transport is provided. `siteId` remains an identity label, not routing.
4. Default timeout is 2000 ms (allowed 100–10000). `port` is optional, default 9.
   Repeated IDs and MACs, zero/multicast MACs, malformed config and public IPv4
   destinations are rejected. No credential or pairing is needed for a standard
   magic packet; this protocol does not authenticate the target.

For a later build, first build the updated device-management dependency (it
adds `computer` to the existing kind enum), then check/test/build this package:

```sh
pnpm --filter @infinitecable2/openclaw-device-management build
pnpm --filter @infinitecable2/openclaw-wake-on-lan check
pnpm --filter @infinitecable2/openclaw-wake-on-lan test
pnpm --filter @infinitecable2/openclaw-wake-on-lan build
```

Source tests can run before any build: the Vitest configuration resolves the
public policy dependency to its current source for tests only. Runtime code
continues to import the published `/policy` export. No compiled output is
generated by the tests or the `check` (`--noEmit`) command.

Stage the immutable package with `dist/`, `device-provider.json`, its native
manifest and the device-management workspace runtime dependency. Use the same
validated package directory in OpenClaw's plugin loading configuration and in
`device-management.config.providers["wake-on-lan"]`. Copying only `dist/` is
insufficient. Validate the registry and provider configs together before any
separately authorized activation. Existing devices and the Google TV plugin's
tested `power_on` wake behavior are unchanged; this adds an independently
assignable generic capability.

## Outcome and limits

The standard packet is six `FF` bytes followed by sixteen repetitions of the
six-byte MAC (102 bytes). There is exactly one UDP send per tool invocation.
Cancellation, timeout and send errors close the operation's socket and timer;
they do not cause a retry. Never automatically retry an ambiguous failure.
At most eight sends may be pending per loaded provider module; there is no
queue. Excess concurrent requests fail with `wake_busy` before socket creation.

Success returns `wakeSent: true`, `confirmed: false`, `online: "unknown"`:
the local UDP stack accepted the datagram, **not** proof of delivery, power-on,
boot completion or service readiness. Do not tell the user the computer is
running solely from this response. Errors expose only bounded codes, not
endpoints, OS errors or configuration contents. Tests use fake sockets and
synthetic configuration; they never send real magic packets.
